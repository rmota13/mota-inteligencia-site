Diagnóstico aprovado com ajustes obrigatórios antes da implementação.

A análise técnica está consistente, mas quero que o plano final incorpore as seguintes decisões de arquitetura, conteúdo e posicionamento.

Não altere arquivos ainda. Primeiro atualize o plano com estas definições e apresente a versão consolidada.

==================================================
1. USAR “PROJETOS”, NÃO “CASES”, NAS ROTAS PÚBLICAS
==================================================

A comunicação institucional deve utilizar prioritariamente:

- Projetos;
- Projetos de Engenharia;
- Projetos selecionados;
- Projeto em destaque.

“Case” pode aparecer pontualmente no texto como estudo de caso, mas não deve ser a nomenclatura principal da navegação ou das rotas.

Alterar a proposta de:

/cases
/cases/[slug]

para:

/projetos
/projetos/[slug]

A rota principal deve ser:

/projetos/sap-commerce-integration-platform

Motivo:

“Projetos” é mais natural em português, mais institucional e representa melhor a profundidade das entregas.

==================================================
2. ESTRUTURA PRINCIPAL DE NAVEGAÇÃO
==================================================

A navegação principal inicial deve ser:

- Início;
- Projetos;
- Soluções;
- Insights;
- Sobre;
- Contato.

Tecnologias não precisa obrigatoriamente ser uma página principal do menu. Pode existir como seção, página de apoio ou conteúdo contextual ligado a projetos e soluções.

Evitar um menu excessivamente extenso.

==================================================
3. PÁGINA DE TECNOLOGIAS
==================================================

Não criar uma simples “parede de logos”.

Caso a rota /tecnologias seja mantida, ela deverá explicar:

- em quais contextos cada tecnologia é usada;
- qual papel ela desempenha;
- quais projetos a utilizam;
- como se integra às demais camadas;
- qual problema ajuda a resolver.

As tecnologias devem ser agrupadas por capacidade:

- ERP e plataformas;
- integrações e APIs;
- dados e analytics;
- automação;
- infraestrutura e observabilidade;
- Microsoft 365;
- IA aplicada.

==================================================
4. GITHUB E PORTFÓLIO TÉCNICO
==================================================

Não criar obrigatoriamente uma rota /github nesta primeira implementação.

Criar inicialmente uma seção institucional de GitHub e portfólio técnico na Home e/ou na página Sobre, com:

- perfil público;
- projeto principal;
- repositórios selecionados;
- descrição do que é público e verificável;
- CTA para o GitHub.

A arquitetura deve permitir uma futura página de projetos open source, mas não deve depender de consultas em tempo real à API do GitHub nesta fase.

Não exibir estrelas, datas ou métricas dinâmicas sem necessidade.

==================================================
5. METODOLOGIA DE ENTREGA
==================================================

Incluir uma seção chamada:

“Como trabalho”

ou:

“Da arquitetura à operação”

1. Diagnóstico;
2. entendimento do processo;
3. arquitetura;
4. modelagem;
5. implementação;
6. integração;
7. deploy;
8. observabilidade;
9. sustentação;

Essa seção pode inicialmente existir na Home ou em Sobre.

Não criar uma rota própria /metodologia na primeira fase, salvo justificativa clara.

==================================================
6. HERO E POSICIONAMENTO
==================================================

O Hero não deve mais ter Power BI como elemento central.

Mensagem principal preferencial:

“Arquitetura de integrações, automação e dados para empresas que querem escalar.”

Submensagem:

“Projetamos soluções que conectam ERP, APIs, marketplaces, Microsoft 365, dados e inteligência artificial para eliminar processos manuais, reduzir riscos e aumentar a eficiência operacional.”

O Hero deve comunicar imediatamente:

- arquitetura;
- integrações;
- automação;
- ERP;
- APIs;
- dados;
- plataformas;
- IA aplicada.

Power BI continua presente, mas como parte da capacidade de dados e analytics.

==================================================
7. ELEMENTO VISUAL DO HERO
==================================================

O dashboard ilustrativo atual não deve ser removido de forma precipitada.

Primeiro:

- verificar se ele ainda comunica valor;
- preservar sua força visual;
- evitar perda da identidade já validada.

Avaliar sua evolução para uma representação arquitetural baseada no projeto principal, por exemplo:

Marketplace
→ Webhook
→ Fila
→ n8n
→ FastAPI
→ SAP Business One
→ Módulo financeiro
→ Conciliação

Essa representação deve ser visualmente sofisticada, mas não pode:

- expor endpoints;
- inventar dados;
- parecer um diagrama técnico cru;
- prejudicar mobile;
- usar animações excessivas.

A substituição deve ser apresentada como proposta visual antes de remover o dashboard atual.

==================================================

- Insights: notas técnicas menores, aprendizados e decisões.

Não criar páginas vazias em produção.

Se não houver conteúdo publicado no lançamento:

- preparar a arquitetura;
- não incluir rotas vazias no menu;
- não incluir drafts no sitemap;
- não apresentar seções sem conteúdo.

==================================================
13. PRIVACIDADE E CONSENTIMENTO
==================================================

A recomendação de privacidade foi aceita, mas a implementação deve ser proporcional.

Antes de criar um banner de cookies complexo:

1. identificar exatamente quais cookies e mecanismos são utilizados;
2. revisar GA4 e Microsoft Clarity;
3. avaliar requisitos aplicáveis ao contexto brasileiro;
4. criar uma política de privacidade clara;
5. propor um mecanismo de consentimento simples e tecnicamente correto.

Não instalar uma plataforma pesada de consentimento sem necessidade.

Não remover analytics antes da aprovação.

==================================================
14. SEGURANÇA DOS ASSETS
==================================================

A auditoria dos arquivos em public/ passa a ser prioridade zero.

Antes de publicar páginas detalhadas:

- gerar inventário dos assets sensíveis;
- indicar quais possuem nomes, valores, documentos, URLs, SQL ou contexto identificável;
- não excluir automaticamente;
- criar uma lista de ações:
  - manter;
  - sanitizar;
  - substituir;
  - mover para fora de public;
  - remover após aprovação.

Arquivos em public/ continuam acessíveis mesmo quando não estão referenciados pela interface.

Nenhuma remoção deve ocorrer sem relatório prévio.

==================================================
17. HEADER E HERO
==================================================

O problema do selo atrás do Header é uma regressão conhecida e deve fazer parte da Fundação.

A solução deve ser estrutural.

Avaliar:

- Header com altura explícita ou mensurável;
- variável CSS compartilhada, como --header-height;
- Hero com padding-top calculado a partir da altura real;
- evitar transformações negativas;
- evitar escadas arbitrárias de seis breakpoints;
- considerar Windows com escala 125% e 150%;
- garantir que o selo permaneça no fluxo normal;
- testar menu mobile.

Não reduzir a logo arbitrariamente.

Antes e depois devem ser documentados com screenshots nas resoluções definidas.
